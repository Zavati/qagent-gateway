# 08.1.7-C-FIX-1 — Recuperação da verificação após falha técnica

## Escopo

Gateway somente, sobre a entrega 08.1.7-C. Recupera uma verificação vinculada que terminou em timeout HTTP, sem registrar uma verificação. Não altera o Test Design, assertions, Results históricos, Runner, Evolution, Registry, Console, Orchestrator, timeout HTTP, prompts ou assessment da IA. Sem migration, dependência, variável ou serviço novo. Não implementa D.

## API

Rota existente:

```http
POST /v1/console/projects/{projectId}/test-evolution/resolutions/verify
Content-Type: application/json
```

Para solicitar a primeira verificação, o body existente continua válido:

```json
{"proposalIds":["tep_example"],"confirmExecution":true}
```

Para autorizar uma nova tentativa após timeout:

```json
{
  "proposalIds": ["tep_example"],
  "confirmExecution": true,
  "retryOfRunId": "run_bounded_timeout"
}
```

Essa chamada pode criar e enfileirar uma execução real. Requer usuário owner/admin/member, confirmação explícita e, em retry, exatamente uma proposta. Não aceita versionId, environmentId, scenarioIds, attemptNumber, readiness, proof ou chave interna no body. O servidor resolve o alvo pela proposta aplicada e sua execução fonte. `retryOfRunId` é uma precondição: identifica o Run vinculado que está sendo recuperado, não autoriza o cliente a mudar o vínculo.

Não fornecer uma nova Idempotency-Key para controlar a tentativa; a rota calcula a chave canônica no servidor. A rota pública `/runs` passa a recusar a namespace `test-evolution-rerun:` com `RUN_IDEMPOTENCY_NAMESPACE_RESERVED`. Isso não reescreve Runs antigos e não promove Runs manuais a verificações.

## Resultado

O envelope externo continua `qagent.learning-resolution.v1`, `operation=VERIFY`. Inspecionar cada item, não apenas `status=ok` do envelope.

```json
{
  "proposalId": "tep_example",
  "status": "CREATED",
  "runId": "run_new",
  "runStatus": "QUEUED",
  "testDesignVersionId": "tdv_applied",
  "verificationAttempt": {
    "contractVersion": "qagent.evolution-verification-attempt.v1",
    "attemptNumber": 2,
    "maxAttempts": 3,
    "retryOfRunId": "run_bounded_timeout",
    "retryReason": "RUNNER_HTTP_TIMEOUT",
    "idempotentReplay": false
  }
}
```

`CREATED` significa um novo Run; não significa execução aprovada. Reenviar o mesmo body retorna o mesmo Run com `status=REUSED` e `idempotentReplay=true`, inclusive se ele já terminou. Uma tentativa em andamento não autoriza outra. Para avançar após outro timeout elegível é necessário referenciar explicitamente o novo Run terminal em `retryOfRunId`.

Sem `retryOfRunId`, a primeira tentativa mantém a chave legada. Se já houver recibo de sucesso, retorna `VERIFIED`. Recibo de resultado não verificado/bloqueado retorna `VERIFICATION_RECORDED`, não um falso `VERIFIED`.

## Elegibilidade conservadora

São necessárias as duas flags existentes no Gateway:

```text
SCENARIO_READINESS_V2_ENABLED=true
SCENARIO_READINESS_RECONCILIATION_ENABLED=true
```

Manter as mesmas flags ativas no Evolution C para validar a evidência posterior. Registry permanece na versão compatível C, sem nova flag para este fix.

O retry exige proposta APPLIED, versão aplicada existente, mesmo tenant/projeto/endpoint/cenário/ambiente, artefatos íntegros e uma cadeia válida de Runs vinculados. A operação deve ser GET, HEAD ou OPTIONS; OBSERVED_BASELINE e métodos mutáveis não ganham retry por essa via.

Primeira política suportada:

- Run terminal `ERROR` com runtime pronto e etapa HTTP concluída.
- Exatamente uma request, zero respostas, um timeout `RUNNER_HTTP_TIMEOUT`, zero redirects e zero erros de rede genéricos.
- Todas as assertions `NOT_EVALUATED` por `ASSERTION_HTTP_RESPONSE_UNAVAILABLE`; nenhuma assertion aprovada ou falha.
- Results correspondente corrobora o timeout, os identificadores, método, índices e tipos das assertions do plano congelado.
- Intervalo mínimo de 30 segundos depois do término da tentativa anterior.
- No máximo três Runs vinculados: inicial + dois retries explícitos.
- Nenhum recibo anterior de outcomeVerification pode ser sobrescrito.

Erro funcional/401 inesperado/404/500 avaliado, generic network error, cancelamento, execução ativa, falta de evidência, auth inválida, contrato inconsistente ou `ERROR` sem diagnóstico não tornam o Run elegível. Não se aumenta timeout nem se força READY para viabilizar retry.

Os códigos mais relevantes são `LEARNING_VERIFICATION_RETRY_RUN_NOT_TERMINAL`, `LEARNING_VERIFICATION_RETRY_NOT_ELIGIBLE`, `LEARNING_VERIFICATION_RETRY_EVIDENCE_INVALID`, `LEARNING_VERIFICATION_RETRY_COOLDOWN` (com `retryAfterSeconds`), `LEARNING_VERIFICATION_RETRY_LIMIT_REACHED`, `LEARNING_VERIFICATION_RETRY_RECEIPT_EXISTS`, `LEARNING_VERIFICATION_RETRY_RUN_NOT_LINKED` e os diagnósticos de scope/link/hash/chain. O item de erro não retorna payloads internos ou segredos.

## Idempotência, persistência e concorrência

Chaves internas canônicas (não fornecidas pelo navegador):

```text
Inicial: test-evolution-rerun:<proposalId>:<appliedVersionId>
Retry 1: test-evolution-rerun:<proposalId>:<appliedVersionId>:attempt:2
Retry 2: test-evolution-rerun:<proposalId>:<appliedVersionId>:attempt:3
```

A restrição UNIQUE existente de organization/project/idempotency e o batch de criação dos artefatos elegem um único Run para cada ordinal. Solicitações concorrentes para o mesmo predecessor convergem para esse registro. A consulta limitada aos três ordinais dispensa migration ou backfill. Não se promete entrega de fila exactly-once: o transporte continua at-least-once, com os claims já existentes do Runner.

A tentativa anterior permanece intacta. O successor usa uma nova materialização normal, recalculando dados/auth e mantendo as validações existentes. O runtime confirmado é obtido da execução fonte original; não se reaproveitam cookies, credenciais nem valores resolvidos do timeout como autorização. Um root pré-C em REGRESSION pode gerar LEARNING quando a versão derivada está pendente, seguindo a regra C já existente.

Em falha de envio à fila depois da persistência, reenviar o mesmo body tenta despachar o mesmo Run `CREATED/PENDING`, sem criar outro. Runs terminais nunca são reenfileirados por esse caminho.

## Verificação e maturidade

A fila de resultados reconhece o novo formato e valida a cadeia antes de chamar o `verify-outcome` existente. Não abre outra investigação/assessment IA para a tentativa de verificação. O endpoint explícito de verify-outcome faz a mesma checagem de associação antes da chamada ao Evolution.

O Evolution C continua responsável por versão, ambiente, cenário, request/auth, assertions e evidência; o retry não enfraquece esses controles. Com resultado utilizável e todos os critérios satisfeitos, persiste o recibo existente, e a reconciliação pode projetar VERIFIED/COMPLETE/regression READY. Um timeout não produz essa promoção. O Test Design histórico permanece imutável, inclusive sua marca PENDING_VERIFICATION.

Se já existe um recibo imutável de outra tentativa (incluindo VERIFICATION_BLOCKED emitido por um deployment anterior), este fix rejeita uma nova criação com RECEIPT_EXISTS. A recuperação de recibos já persistidos exige um desenho específico e não foi incluída. O caso validado para esta entrega tinha `outcomeVerification=null`.

## Aplicação e rollback

Publicar somente Gateway atualizado. Integrar CHANGED-FILES sobre a base C, usando pré-verificação dos hashes. Não substituir configurações locais/ambiente pelos arquivos do ZIP indiscriminadamente. Nenhuma configuração está alterada pelo fix. Manter Evolution e Registry C publicados e as flags atuais.

```sh
npm run test:f08-1-7-c-fix1
npm run test:f08-1-7-c
```

Depois do deploy, solicitar retry explicitamente e acompanhar o Run novo pelo GET normal. Aguardar o evento de resultados; consultar a proposta e a reconciliação da versão aplicada no mesmo ambiente. Se necessário, usar verify-outcome explicitamente com os IDs reais do Run vinculado e de seu Result Set. Não usar o PASS manual ou o Run da versão fonte como substituto.

Não voltar o Gateway para código pré-fix com retries em andamento: o parser antigo não reconhece as chaves de tentativa. Desligar a flag C impede novas solicitações deste retry, mas também suspende os caminhos C existentes. Se um evento de retry for entregue com C desligada, a checagem falha fechado; depois de reativar, a verificação explícita do Run vinculado permite retomar sem gerar nova execução. O rollback de arquivos é disponibilizado para retorno controlado, não como garantia de compatibilidade de uma versão antiga com registros novos. Nenhum Run/Result/recibo deve ser apagado.

## Limites da validação

Testes locais usam SQLite real e módulos reais; HTTP, Results e autenticação do teste são sintéticos. O Runner não é executado na integração C-FIX-1. Não há deploy, fila remota, provider IA ou chamada à aplicação monitorada. O aceite real do retry e os smokes C de cobertura/outros endpoints continuam separados. A pendência B coverage PARTIAL não é marcada como homologada pelos testes locais.
